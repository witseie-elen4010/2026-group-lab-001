# ADR 006: Password Hashing with Node.js Built-in scrypt

## Context

ADR 002 established that user accounts are stored in MongoDB Atlas with a `passwordHash`
field, and that authentication routes must read and write through dedicated model helpers
rather than querying the database directly. It did not specify how passwords should be
hashed or verified, leaving that decision to be formalised before the authentication layer
was implemented.

The application supports two sign-in methods:

- **Local authentication:** a user submits a username and password, which must be verified
  against a stored hash
- **Google OAuth:** a user signs in via their Google account, in which case no password is
  stored or required

Both paths share the same `User` collection. The `passwordHash` field must therefore be
optional at the schema level to accommodate Google-only accounts, but must be stored
securely whenever a local password is set.

The hashing approach must satisfy the following requirements:

- Passwords must never be stored in plain text or with a reversible encoding
- The algorithm must be resistant to brute-force and dictionary attacks, including attacks
  with GPU acceleration
- Each stored hash must include a unique, randomly generated salt to prevent precomputed
  rainbow-table attacks
- Password verification must not leak timing information that could be used to infer
  whether a partial hash match occurred

A zero-dependency solution is preferred, given the project's existing policy of keeping
the dependency surface small where built-in alternatives are available.

## Decision

We have decided to use the **`scrypt` function from Node.js's built-in `node:crypto`
module** for all local password hashing and verification. No third-party password library
(such as `bcrypt` or `argon2`) is introduced.

The implementation is encapsulated in `src/utils/password.js` and structured as follows:

- **Algorithm:** `scrypt`, accessed via `node:crypto`. scrypt is a memory-hard key
  derivation function specifically designed to be costly to attack with custom hardware
- **Salt:** A 16-byte cryptographically random salt is generated using `randomBytes` from
  `node:crypto` for every new password. The salt is encoded as a hex string
- **Derived key length:** 64 bytes (512 bits), providing a large output space that exceeds
  the effective entropy of most passwords
- **Storage format:** The salt and derived key are stored as a single colon-delimited
  hex string (`<salt>:<derivedKey>`) in the `passwordHash` field of the `User` document
- **Verification:** `timingSafeEqual` from `node:crypto` is used to compare the freshly
  derived key against the stored key, preventing timing side-channel attacks
- **Failure handling:** If the stored hash string does not contain the expected
  salt-and-key structure, `verifyPassword` returns `false` without throwing, ensuring
  that malformed records are rejected gracefully
- **Google OAuth accounts:** Users who register exclusively through Google Sign-In do not
  have a `passwordHash` field. The login route detects this and directs them to use
  Google Sign-In rather than attempting password verification. The `User` collection
  schema was updated via migration to make `passwordHash` optional

## Consequences

### Pros

- **No additional dependencies:** `scrypt`, `randomBytes`, and `timingSafeEqual` are all
  part of the Node.js standard library. No third-party package is needed, reducing
  supply-chain risk and removing an ongoing maintenance burden.
- **Memory-hard by design:** scrypt is specifically designed to require significant memory
  during computation, making large-scale brute-force attacks with GPUs or ASICs
  substantially more expensive than with simpler algorithms such as SHA or MD5.
- **Unique salt per password:** Generating a fresh 16-byte random salt for every hash
  ensures that two users with identical passwords produce different stored values and that
  precomputed lookup tables cannot be used.
- **Timing-safe comparison:** Using `timingSafeEqual` eliminates the risk of a
  timing-based side-channel attack during verification, which a naive string equality
  check would not prevent.
- **Clean utility boundary:** Isolating hashing and verification in a single module
  (`src/utils/password.js`) makes the logic independently testable and keeps password
  handling out of route and model code.

### Cons

- **No built-in parameter tuning API:** Unlike `argon2` library wrappers, the Node.js
  `scrypt` implementation does not expose a convenience method to select a named security
  level. The cost parameters (`N`, `r`, `p`) must be configured explicitly if defaults
  need to be changed. The current implementation uses Node.js's default cost parameters
  rather than explicitly tuning them.
- **Manual migration path:** If the cost parameters need to be increased in a future
  sprint, existing stored hashes will remain at the old cost level until each user logs in
  and triggers a rehash. No automatic rehash-on-login mechanism is currently implemented.
- **No Google account password fallback:** Users who originally registered with a password
  and later link their Google account retain a `passwordHash`, but the reverse path
  (adding a local password to a Google-only account) is not currently supported. This
  limits account recovery options if Google Sign-In becomes unavailable.

Accepted

## Summary

**Node.js built-in `scrypt`** has been selected as the password hashing algorithm for
local authentication. Salt generation and timing-safe verification are handled entirely
within `src/utils/password.js` using `node:crypto` primitives, with no third-party
password library required. The `passwordHash` field is stored in the `User` collection
as an optional field so that Google OAuth accounts remain fully supported alongside local
password accounts.
