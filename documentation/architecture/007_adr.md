# ADR 007: Google OAuth 2.0 Sign-In with Passport.js

## Context

ADR 006 established that local user accounts are authenticated by verifying a bcrypt-style
`scrypt` hash stored in the `User` collection. That approach requires every user to
choose and remember a password during registration, which adds friction to the sign-up
flow and places the burden of password management on both the user and the application.

As the application grew, two practical concerns emerged:

- **Registration friction:** Requiring a new username and password is a barrier, particularly
  for users who already have a Google account associated with their university email address
- **Account recovery:** A password-only system has no out-of-band recovery path unless a
  separate email-reset flow is built; adding a trusted identity provider offers a
  complementary path

A third-party sign-in option was therefore identified as a useful addition to the
authentication layer. The provider had to satisfy the following requirements:

- It must be widely used and trusted by the application's target audience (university
  students and staff)
- It must return a verified email address that can be used to match against existing
  local accounts
- It must not require storing any OAuth tokens in the application's own database
- It must integrate cleanly with the existing Express.js and `express-session` stack
  without replacing the session management that local authentication already depends on

## Decision

We have decided to add **Google OAuth 2.0** as a second authentication method, implemented
using the **`passport`** middleware framework and the **`passport-google-oauth20`**
strategy.

The integration is structured as follows:

- **Libraries:** `passport` v0.7 and `passport-google-oauth20` v2.0, registered as
  production dependencies
- **Strategy configuration:** `src/config/passport.js` registers a single
  `GoogleStrategy` instance. `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are read from
  environment variables; the callback URL is fixed to `/auth/google/callback`. The
  strategy's verify callback calls `done(null, profile)` directly — no token storage or
  database lookup is performed at this stage
- **Passport initialisation:** `passport.initialize()` is mounted as Express middleware
  in `app.js`. Passport's own session serialisation (`passport.session()`) is
  intentionally **not** used; the application continues to manage its own session through
  `express-session`, ensuring that the authentication state for local and Google users is
  handled identically
- **OAuth routes (`src/routes/auth.js`):**
  - `GET /auth/google` — redirects the user to Google's authorisation page, requesting
    the `profile` and `email` scopes only
  - `GET /auth/google/callback` — receives the authorisation code, exchanges it for a
    profile, then resolves the user identity against MongoDB using the following ordered
    lookup:
    1. Look up the user by `googleId` (fast path for returning Google users)
    2. If not found, look up by the verified email address; if an existing local account
       is found, call `linkGoogleId` to write the `googleId` onto that document so
       future sign-ins follow the fast path
    3. If no matching user exists, store the Google profile data in
       `req.session.pendingGoogle` and redirect to `/register/complete`
  - On a successful match, `req.session.user` is populated with the same fields used by
    local login and the user is redirected to `/home`
- **Profile completion route (`src/routes/register_complete.js`):** New Google users who
  have no matching local account are redirected here to supply a username, role, and
  institution. The resulting document is inserted with the `googleId` field present but
  without a `passwordHash`, consistent with the optional schema introduced in ADR 006
- **Model helpers (`src/models/user_db.js`):** Three helpers support the OAuth flow:
  `getUserByGoogleId`, `getUserByEmail`, and `linkGoogleId`
- **Secrets management:** `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are stored as
  environment variables and are never committed to the repository. In production they are
  configured via the Render dashboard (see ADR 005)

## Consequences

### Pros

- **Reduced registration friction:** Users with a Google account can sign in without
  choosing a password, lowering the barrier to first use.
- **Automatic account linking:** The email-based fallback lookup means that a user who
  previously registered with a local password can later use Google Sign-In with their
  same email address without creating a duplicate account.
- **No token storage:** Access and refresh tokens returned by Google are discarded after
  the verify callback. The application never stores OAuth tokens, which eliminates a
  class of credential-exposure risk.
- **Consistent session model:** Reusing `express-session` for both authentication paths
  means that route guards, flash messages, and session teardown (logout) work identically
  regardless of how the user signed in.
- **Minimal scope request:** Requesting only `profile` and `email` scopes limits the
  personal data retrieved from Google to what is strictly required, reducing privacy
  exposure.

### Cons

- **Third-party dependency for sign-in:** If Google's OAuth endpoints are unavailable,
  Google-only users cannot sign in. Users who have not set a local password have no
  fallback authentication path.
- **No local password fallback for Google-only accounts:** A user who registered
  exclusively through Google cannot fall back to a username/password login if they lose
  access to their Google account. Adding a password-setting flow for such users would
  require additional implementation effort.
- **Client secret rotation overhead:** If `GOOGLE_CLIENT_SECRET` needs to be rotated,
  both the Google Cloud Console configuration and the Render environment variable must be
  updated in a coordinated step; a mismatch will break the entire OAuth flow.
- **Additional dependencies:** Introducing `passport` and `passport-google-oauth20`
  increases the application's dependency surface. Both packages require ongoing
  maintenance and version tracking.
- **Google project configuration is external:** The OAuth consent screen and authorised
  redirect URIs must be managed in the Google Cloud Console separately from the codebase.
  A misconfigured redirect URI will cause callback failures that are not immediately
  obvious from application logs alone.

Accepted

## Date

14/05/2026

## Summary

**Google OAuth 2.0**, integrated through **Passport.js** and the **`passport-google-oauth20`**
strategy, has been adopted as a second authentication method alongside local
username-and-password sign-in. The OAuth flow resolves user identity by looking up the
returning Google account ID first, falling back to email-based account linking for
existing local accounts, and redirecting genuinely new users to a profile completion
page. All session management continues to use `express-session`, and no OAuth tokens are
persisted to the database.
